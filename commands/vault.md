description: Set up the 7IT Guard backup vault for this app: a nightly encrypted copy of the database and stored files into storage the owner owns, a weekly restore test, all in the owner's own GitHub account.
argument-hint: <the app's address, if this project does not name it>
disable-model-invocation: true
---

The person wants the 7IT Guard backup vault for this project. Address, if given: $ARGUMENTS

The rule of this command: one step for the person. Find everything you can in the project yourself and ask only what you cannot find, one short question at a time, each with a default. Never print, repeat or ask the person to paste a password, a database address, a storage key or a private key into this conversation: the helper reads them from the project's env files or from `.7it-vault.env` (a local file it keeps out of git) and passes them straight to `gh secret set`. Plain words with the person: "backup", "copy", "restore test", "your storage", "your key".

The helper: `node "${CLAUDE_PLUGIN_ROOT}/scripts/vault/setup.mjs" <step> ...` (Node 18 or newer, run from the repository root). Each step prints one JSON object.

1. **Look first.** Run the helper's `detect`. It reports the GitHub repository (name, numeric id, default branch, public or private), the platform, the database variable (its name only, and whether GitHub can reach it), stored files (Supabase Storage, an S3 or R2 bucket, or none), the backup storage, the person's time zone, an existing vault, and `missing`.
   - `gh_cli` or `gh_login` missing: tell the person to install the GitHub CLI (https://cli.github.com) or run `gh auth login`, then run this command again. Stop.
   - The app's address: use $ARGUMENTS, else `site_hints`, the deploy config or the README, as the 7IT Guard check does. Ask only if none of them names it.
2. **Lovable Cloud or Bolt Database, before anything else.** If `ask_cloud` is true (a Lovable or Bolt project with no database address), ask one question: "Is your database in your own Supabase account, or in Lovable Cloud / Bolt Database?" If the person is not sure, give the `check` line of `guide --builder <builder>`.
   - Own Supabase: run `ask-db`. Ask the person to paste the Session pooler address (Supabase: Connect, then Session pooler) into that line of `.7it-vault.env` and save the file, never in the chat. Then go on with step 3.
   - Lovable Cloud or Bolt Database: write nothing at all (no workflow file, no key, no secret; `write` refuses anyway). Run `guide --builder <lovable|bolt>` and tell the person, in plain words and in this order: `label` and `why` (a nightly copy cannot run there; backups are manual, not automatic); path 1, `move.title` with `move.text` and the link `move.doc` (for Lovable, offer `move.prompt` as a ready prompt to paste in the Lovable chat of the new project); path 2, `export.title` with `export.text` and the link `export.doc`. Then ask once: "Want a monthly reminder in the 7IT Guard app to press the export button?" With yes, call `vault_register` with `{ "site": "<address>", "manual": "<lovable|bolt>" }` and give the link it returns; if it answers with a message (no key, the plan, the site), pass it on as written. Stop there. Never read, export or copy the app's data yourself, and never say the copy is automatic.
3. **Check the plan.** Call the `vault_register` tool with `{ "site": "<address>", "dry": true }`. Without a 7IT key, or when it says the plan does not include the vault or the site is not on the key, pass its message on as written and stop.
4. **Public repository.** If `repo.visibility` is `public`, say that run logs are public (no data is in them, but times and sizes are) and go on only if the person agrees.
5. **The database address.** If `database.reachable` is false with `supabase_direct`, the helper wrote an empty `VAULT_DATABASE_URL` line into `.7it-vault.env`: ask the person to paste there the Session pooler address (Supabase: Connect, then Session pooler) and save the file. Never ask for it in the chat.
6. **A sign-in that can only read (recommended).** Run `role-sql --repo <repo>`. Show the person the SQL it printed (the password is hidden) and say what it does in one line: a new database sign-in that can read everything and change nothing, used only by the backup. Ask once: "Create it now?"
   - Yes: run `role-run --repo <repo>`. If it answers `no_psql`, give the path of the SQL file and ask the person to paste its contents into their database's SQL editor (Supabase: SQL Editor) and run it, then continue. If the database refused the first grant, say that the file holds the other lines to use.
   - No: keep the existing sign-in.
7. **Storage.** Run `storage --repo <repo> --files <detect.files>`. If it lists `missing`, it wrote those names into `.7it-vault.env` with a hint on each line. Ask the person, in one message, to fill them and save the file: the default is a NEW Cloudflare R2 bucket only for backups, with an access key limited to that bucket; for Supabase stored files, an S3 access key from Supabase (Storage, then S3 access keys). Then run `storage` again.
8. **Keys.** Run `keys --repo <repo>`. Then tell the person, in these words: "Your backup key is in <key_file>. Put it in your password manager now, then delete the file. Without it nobody, including 7IT, can open your backups. Restore tests use a second key that lives in your GitHub secrets; your own key never leaves you." When the vault already existed, the helper keeps both keys, so older backups stay readable.
9. **The database secret.** Run `db-secret --repo <repo>` (add `--readonly` when step 6 created the sign-in).
10. **The two workflow files.** Run `write --repo <repo> --recipient <keys.recipient> --ci <keys.ci> --files <detect.files> --remote-path <storage.remote_path> --remote-kind <storage.remote_kind> --pg <detect.pg> --tz <detect.tz>`. It writes `.github/workflows/7it-vault.yml` and `.github/workflows/7it-vault-restore.yml`: complete files, every step visible, tools pinned. Say where they are and when the backup runs (`schedule.local` in `schedule.tz`), then ask once: "Commit and push them to <default branch>?" With yes, commit only these two files and push. If the branch is protected, open a pull request and ask the person to merge it, then continue.
11. **Register.** Call `vault_register` with `site` and every field of the helper's `register` output, plus `repo_id` (`detect.repo.id`) and `ref` (`refs/heads/<default branch>`). Keep the `open` link it returns.
12. **The first backup.** Run `start --repo <repo>`. It starts the first backup and, right after it, the first restore test.
13. **Clean up.** Ask once: "Remove the setup file .7it-vault.env and the SQL file now?" With yes, run `cleanup --repo <repo>`.
14. **Tell the person, in four short lines:** the first backup is running and the restore test follows; the backup runs every night at <schedule.local>; 14 daily, 8 weekly and 12 monthly copies are kept; open the 7IT Guard app to see "First backup done" within minutes: <open link>.

Running this command again is safe: it keeps both keys and the existing settings, writes the newest workflow files, and renews what failed (a new database password, a storage key, a newer database version). Add `--renew-test-key` to `keys` only when the app says the restore test key must be renewed.

If anything fails, say what failed in one sentence and the one next step. Never change the live database, the live storage or the app's code beyond the two workflow files.
